2. VPC・ネットワーク

今回の検証では、PrivateLink / VPC Endpoint / NAT Gatewayは使用していない。

VPCのルート：

10.0.0.0/16 → local
0.0.0.0/0   → Internet Gateway

DataSync AgentからAWSのPublic Endpointへ接続。

DataSync Agentの接続テストで、

activation.datasync.ap-northeast-1.amazonaws.com:443
cp.datasync.ap-northeast-1.amazonaws.com:443
datasync.ap-northeast-1.api.aws:443

などがすべて NETWORK TEST: PASSED。

3. VPCのDNSを有効化

今回、最初はDNSが無効だった。

EnableDnsSupport = false
EnableDnsHostnames = false

以下で有効化。

aws ec2 modify-vpc-attribute \
  --vpc-id vpc-0c55c5a6d9835e666 \
  --enable-dns-support "{\"Value\":true}"

aws ec2 modify-vpc-attribute \
  --vpc-id vpc-0c55c5a6d9835e666 \
  --enable-dns-hostnames "{\"Value\":true}"

最終的に：

EnableDnsSupport   = true
EnableDnsHostnames = true

6. FSxのSMB共有確認

Windows ServerからDNS確認。

nslookup amznfsxuirt9mbz.nishihara.com

Test-NetConnection amznfsxuirt9mbz.nishihara.com -Port 445

ADユーザーでFSxへ認証。

net use \\amznfsxuirt9mbz.nishihara.com\IPC$ /user:nishihara.com\syncuser *

認証成功後：

net view \\amznfsxuirt9mbz.nishihara.com

結果：

-----
share

11. 障害時の利用確認

今回の検証で最終的に確認したかった部分。

通常：

Windows Server
     ↓
オンプレFS

DataSyncで：

オンプレFS
     ↓
DataSync
     ↓
FSx

障害時：

オンプレFS
   ❌
   
利用者
   ↓
FSx
   ↓
\\amznfsxuirt9mbz.nishihara.com\share

つまり、オンプレ側のファイルサーバーが使用不能になっても、FSxに同期済みのファイルを直接利用できることを確認する。

今回の検証でハマったポイント
① DNS

最初：

EnableDnsSupport = false
EnableDnsHostnames = false

→ 有効化。

② FSxのDNS名を間違えた
amznfsxvlzpspjk.nishihara.com

は管理用。

amznfsxuirt9mbz.nishihara.com

がSMB接続用。

③ shr と share

DataSyncで最初：

/shr/

を指定。

しかしFSxに存在した共有は：

/share/

だった。

そのため、

mount error(2): No such file or directory

が発生。

最終的に /share/ に変更。
